# SQListo Agent

**SQListo Agent** is an offline, natural-language scientific assistant for the **XYZ2DB** molecular-dynamics database system.

It combines:

- a local language model running through `llama.cpp`;
- natural-language routing;
- read-only SQL generation;
- trajectory restoration;
- fragment and reaction analysis;
- theoretical mass-spectrum analysis;
- global fragmentation kinetics;
- frame-by-frame event detection;
- bond-breaking and bond-forming analysis;
- data-quality auditing;
- controlled database-writing operations.

The agent is designed for computational-chemistry workflows in which molecular-dynamics trajectories, simulation metadata, energies, fragments, reactions, and derived descriptors are stored in SQLite.

# Overview

SQListo Agent allows the user to query and analyse an XYZ2DB database using ordinary scientific language.

A user may write:

```text
How many trajectories are stored for each molecule and isomer?
```

or:

```text
Export the Azaconazole trajectory at ZPEx3 in which H+ appears at the latest persistent time.
```

or:

```text
Compare the global fragmentation kinetics of the E and Z isomers of Diniconazole.
```

The user does not need to know SQL or the internal Python function names.

The agent interprets the request, chooses one registered scientific action, validates the requested molecule, isomer, method, and energy label against the real database catalogue, and then executes deterministic Python or read-only SQL.

---

# How the agent works

The system follows this workflow:

```text
Natural-language question
          |
          v
Local LLM tool router
          |
          v
Structured JSON plan
          |
          v
Python validation
          |
          +----------------------------+
          |                            |
          v                            v
Read-only SQL                    XYZ2DB scientific tool
          |                            |
          +-------------+--------------+
                        |
                        v
        Terminal result, CSV, XYZ, plot, or audit report
```

The language model does **not** execute arbitrary Python or shell commands.

It only selects from a closed set of allowed actions, such as:

```text
sql_query
trajectory_details
fragment_first_appearance
mass_spectrum
compare_global_kinetics
export_event_window
database_audit
```

Python then validates and executes the selected action.

## Router output

When `--show-plan` is enabled, the agent prints the JSON plan generated by the local model.

Example:

```json
{
  "action": "export_fragment_event_trajectory",
  "arguments": {
    "molecule": "Azaconazole",
    "isomer": null,
    "method": null,
    "energy_label": "ZPEx3",
    "formula": "H+",
    "persist_frames": 5,
    "selection": "latest"
  }
}
```

This is useful for verifying that the model has interpreted the request correctly.

# Scientific scope

SQListo Agent is intended for databases containing:

- molecular-dynamics trajectories;
- fixed atom ordering across trajectory frames;
- coordinates stored in compressed frame blocks;
- per-frame comments, energies, and times;
- simulation input metadata;
- molecule, isomer, method, and energy labels;
- final-frame fragment analyses;
- trajectory-level descriptors;
- aggregated reaction patterns;
- theoretical mass-spectrum data;
- global precursor-disappearance kinetics.

The system can work with labels such as:

```text
Molecule: Azaconazole
Isomer: E, Z, cis, trans
Method: PM6, uB3LYP, B3LYP
Energy: ZPEx2, ZPEx3, De, D0
```

Only labels that actually exist in the database are accepted.

## `sqlisto_agent.py`

Main agent entry point.

Responsibilities:

- load the database catalogue;
- call the local LLM router;
- validate the returned JSON;
- execute SQL or scientific tools;
- export files to a safe output directory;
- protect database-writing operations.

## `sqlisto_tools.txt`

Compact tool manual included in the LLM routing prompt.

It explains:

- available actions;
- scientific meanings;
- supported parameters;
- fragment scopes;
- safety restrictions.

## `xyz2db_assistant.py`

Existing natural-language-to-SQL component.

It is used when the selected action is:

```text
sql_query
```

## `sqlisto_knowledge.txt`

Semantic database manual used by the SQL generator.

It should document:

- table meanings;
- relationships;
- scientifically correct counting rules;
- distinctions such as charged fragments versus `Cl+`;
- when a frame-level Python tool is required.

Display the JSON tool plan generated by the router.

```bash

```

This option is strongly recommended during development and testing.

Display generated SQL when the selected action is `sql_query`.

```bash
--show-sql
```

### `--show-repairs`

Show SQL-repair attempts after SQLite validation errors.

```bash
--show-repairs
```

### `--router-tokens`

Maximum token budget for the tool-selection model output.

```bash
--router-tokens 240
```

The router should only return a compact JSON object, so a small value is normally sufficient.

### `--sql-tokens`

Maximum token budget for SQL generation.

```bash
--sql-tokens 96
```

### `--timeout`

Timeout in seconds for each local-model call.

```bash
--timeout 600
```

Frame-scanning analyses are performed by Python after routing and are not limited by this model timeout.

### `--max-rows`

Maximum number of rows added to ordinary SQL queries when appropriate.

```bash
--max-rows 200
```

### `--allow-write`

Allow actions that modify the database.

```bash
--allow-write
```

Without this option, protected write operations are rejected.

# Database filters

Most actions support these filters:

```text
molecule
isomer
method
energy_label
```

They may be combined.

Example:

```text
Molecule: Diniconazole
Isomer: E
Method: uB3LYP
Energy: ZPEx3
```

Natural-language request:

```text
List all uB3LYP trajectories for the E isomer of Diniconazole at ZPEx3.
```

The agent validates every filter against the actual values stored in the database.

If the database contains:

```text
E
Z
```

and the user requests:

```text
isomer R
```

the action fails with a list of valid isomer labels.

---

## Unspecified filters

An omitted or null filter means all available values.

For example:

```text
Export all trajectories containing CO+ for every molecule and energy.
```

is interpreted as:

```json
{
  "molecule": null,
  "isomer": null,
  "method": null,
  "energy_label": null,
  "formula": "CO+"
}
```

Generated files are placed inside the configured output directory.

Default:

```text
outputs/
```

Depending on the action, outputs may include:

- `.xyz` trajectory files;
- frame-level `.csv` files;
- event-summary `.csv` files;
- manifests;
- reaction tables;
- theoretical spectra;
- PNG, PDF, or SVG plots;
- restored input files.

## Frame-data CSV

A restored trajectory normally receives a frame-data file containing:

```text
frame_idx
frame_number
energy
time_ps
```

## Atom numbering

Atom indices reported in broken or formed bonds are **1-based**.

Example:

```text
C12-N15
```

This means:

- carbon atom at XYZ line/index 12;
- nitrogen atom at XYZ line/index 15.

The numbering corresponds to the fixed atomic ordering in the stored trajectory.

# Core query tools

## `sql_query`

### Purpose

Answer relational questions directly from SQLite using generated read-only SQL.

### Appropriate questions

```text
How many trajectories are stored for each molecule?
```

```text
Which trajectory has the largest number of frames?
```

```text
What percentage of trajectories contains HCl?
```

```text
List trajectories with more frames than the database average.
```

### Example command

```bash
python sqlisto_agent.py \
  DBs/azc_dfcz_ub3_z3.db \
  "How many trajectories are stored for each molecule and isomer?" \
  --show-plan \
  --show-sql
```

### Notes

- SQL is validated before execution.
- Only read-only `SELECT` or `WITH` statements are allowed.
- The SQL subsystem can repair syntax or schema errors.
- Frame-level geometric analyses are not delegated to SQL.

# Fragment-event and bond-analysis tools

## Fragment scopes

Several tools accept a conceptual fragment scope.

### `final_frame`

Use fragment information already stored from the final analysed frame.

Advantages:

- fast;
- no full trajectory scan.

Limitation:

- transient fragments are not detected.

### `any_frame`

Scan the full trajectory and accept the fragment if it appears in at least one frame.

Advantages:

- finds transient species.

Cost:

- every frame must be decompressed and analysed.

### `persistent`

Scan the full trajectory and require the fragment for a specified number of consecutive frames.

Parameter:

```text
persist_frames
```

This reduces sensitivity to one-frame connectivity fluctuations.

# Broken- and formed-bond analysis

Bond changes are calculated in memory and are not stored in new database tables.

## Procedure

For a fragment event at frame \(f\):

1. reconstruct frame \(f-1\);
2. reconstruct frame \(f\);
3. build connectivity for both frames;
4. create a set of atom-index pairs for each frame;
5. calculate:

\[
\text{broken bonds} = B_{f-1} \setminus B_f
\]

\[
\text{formed bonds} = B_f \setminus B_{f-1}
\]

## Output convention

Example:

```text
broken_bonds_text: C12-N15; C7-H34
formed_bonds_text: N15-H34
```

The atom number is 1-based and corresponds to the atom order in the trajectory XYZ.

## Important interpretation

The detected changes are **geometric connectivity changes** based on XYZ2DB’s distance cutoff.

They are not bond orders calculated from an electronic wavefunction.

A bond may appear to break or form if a distance crosses the connectivity threshold.

Persistent event detection helps reduce one-frame fluctuations, but bond-change interpretation should still be checked visually.

# Scientific definitions and assumptions

## Fragment detection

Fragments are detected from connected components in a geometry.

Two atoms are considered connected when their distance is below a cutoff based on atomic radii and the configured bond factor.

Therefore, fragment identity is geometric and depends on the chosen cutoff.

---

## Formula and charge convention

XYZ2DB builds formulas from fragment atom symbols using a fixed formula order.

The charge label is assigned using the accepted `charge_guess` convention already defined in the project.

Examples:

```text
H+
Cl+
CO+
C3H5N3
```

This is an operational classification used consistently throughout the database workflow.

---

## First persistent appearance

For a target fragment and persistence requirement \(p\):

1. scan frames in chronological order;
2. identify frames containing the target formula;
3. locate the first sequence of at least \(p\) consecutive matching frames;
4. assign the event time to the first frame in that sequence.

---

## Censoring

In global kinetics, a trajectory that does not display a persistent fragmentation event during its observation interval is treated as censored.

It is not automatically interpreted as chemically stable at infinite time.

---

## Final-frame reactions

Reaction frequencies are based on fragments detected in the last analysed frame.

A reaction UID identifies a stable, normalised final fragment set.

This representation is appropriate for final-product statistics but does not itself encode an elementary reaction mechanism.

---

## Mass spectra

The theoretical mass spectrum is derived from stored final-fragment counts.

It is not an ab initio ionisation-intensity calculation.

Peak intensity is a relative frequency-based quantity.

---

## Fixed atomic ordering

The trajectory parser requires the number, identity, and order of atoms to remain constant between frames.

This makes it possible to report atom numbers consistently across:

- event frames;
- previous frames;
- full trajectories;
- broken-bond analysis;
- exported XYZ files.

---

# Performance considerations

## Fast operations

Usually fast because they use indexed SQLite records:

- `sql_query`;
- `database_summary`;

- `trajectory_details` without frame scanning;
- `fragment_search`;

## Potentially expensive operations

These scan full trajectories:

- `fragment_first_appearance`;
- `export_fragment_event_trajectory`;
- `export_trajectory_with_fragment` with `any_frame`;
- `export_all_trajectories_with_fragment` with `any_frame`;
- persistent fragment searches;
- event-frame export;
- event-window export;
- fragment timelines;
- fragment lifetimes;
- fragment event counts;
- global kinetics;
- kinetics comparisons;
- fragment-appearance comparisons.

## Recommendations

- filter by molecule, isomer, method, and energy whenever possible;
- use `final_frame` when scientifically appropriate;
- use `persist_frames=1` only when single-frame detection is intended;
- use `persist_frames=5` or another justified value for stable events;
- avoid exporting every matching trajectory before first counting matches;
- use `--timeout 600` for local-model calls on slower machines;
- remember that Python frame scanning may continue after routing completes.

- keep the LLM responsible only for intent interpretation;
- keep scientific calculations deterministic;
- validate labels against the database;
- restrict filesystem outputs;

# Current limitations

1. **Product-specific rate constants** are not yet equivalent to the implemented global precursor-disappearance kinetics.

2. **Reaction summaries** represent final-frame fragment sets, not full mechanistic networks.

3. **Fragment charge** follows the project’s accepted `charge_guess` convention rather than a separate electronic-charge calculation.

4. **Bond changes** are geometric connectivity changes and should be visually inspected.

5. **Mass-spectrum intensities** are frequency-derived theoretical intensities, not experimentally calibrated ion yields.

6. **Natural-language routing** may occasionally select an imperfect action, especially with a small local model. `--show-plan` is recommended.

7. Some comparison actions may recompute analyses repeatedly and can be expensive.

8. `global_kinetics` writes kinetic summaries and events to the database through the existing XYZ2DB function.

9. Write protection currently applies explicitly to fragment and reaction storage actions; database backups remain recommended before any analysis that stores results.

# Summary

SQListo Agent is not a collection of hard-coded questions.

It is a controlled scientific-agent architecture in which:

- the local LLM interprets the request;
- the router chooses one general capability;
- Python validates all filters and parameters;
- deterministic XYZ2DB functions perform the analysis;
- results are displayed or exported;
- potentially destructive operations are protected.

The same tool can therefore answer many differently worded questions in English or Spanish, provided the requested scientific operation is represented by one of the registered actions.
